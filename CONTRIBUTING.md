# Contributing

Thanks for looking. LANDA.SH is small and opinionated: a calm dashboard first,
running entirely on one small dongle. Changes that keep it that way are very
welcome.

## Before you start

Read [CLAUDE.md](CLAUDE.md). It is the developer's guide, written for AI coding
agents and people alike: the module map, the conventions every file follows,
the version-numbering scheme, and a list of traps that each cost real time to
find. The sections on the HTTP server, the scanner and updates are worth
reading before touching any of those.

For anything bigger than a fix, please open an issue first, so we can agree the
shape of it before you spend time on code.

## Building

You need [ESP-IDF v5.5](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32c6/get-started/)
and, to run it, a Waveshare ESP32-C6-GEEK.

```bash
idf.py set-target esp32c6    # once
idf.py build
idf.py -p <port> flash monitor
```

Options live under **NetDash** in `idf.py menuconfig`. Before flashing a
build of your own, set `CONFIG_NETDASH_OTA_REPO` to a releases repository you
control, or empty to disable updates. Otherwise the dongle will replace your
build with the maintainer's next release.

The dashboard is one file, `main/web/www/index.html`, embedded in the
firmware at build time. To work on it without hardware:

```bash
python tools/mock_api.py     # then open http://127.0.0.1:8080
```

## The rules that matter most

- **The API comes first.** [docs/API.md](docs/API.md) is the contract between
  the firmware and the page. Change it before changing either side.
- **Memory is the constraint.** There is no PSRAM, and the dongle runs with
  75-90 KB of heap free, which an update's HTTPS download needs most of.
  No dynamic allocation in hot paths, no large stack buffers, and stream big
  responses.
- **Stored data must survive updates and rollbacks.** Settings are one blob
  that only ever grows at the end; other stored records are versioned. Never
  reorder or resize a stored field. See the settings header.
- **Each module owns its files.** Add what you need to another module's
  header rather than reaching into it.
- **Keep the dashboard calm.** New information should earn its place on the
  page; most of it belongs behind a click, in the notification feed, or at
  the Hacker detail level.
- `main/net/oui_table.inc` is generated by `tools/gen_oui.py`. Never edit it
  by hand.

## Testing

- Build without warnings. The build treats most warnings as errors anyway.
- With a dongle on your network, `python tools/smoke_test.py http://landash.local`
  exercises every endpoint and checks the responses against the API
  documentation. It refuses to touch a credential vault that already exists.
- For changes to scanning, test from a **cold boot**, not a warm one. A sweep
  that only has to keep already-found devices online passes where a sweep that
  has to find them from scratch fails.
- Describe what you tested on real hardware in your pull request.

## Commits and pull requests

- One logical change per commit, with a message that says why, not only what.
- Check `git diff dependencies.lock` before committing. A fresh build
  directory can rewrite it with paths from your machine; see CLAUDE.md.
- Do not commit `sdkconfig`, `build/` or `managed_components/`.
- Releases, tags and version numbers are handled by the maintainer; see the
  version-numbering section of CLAUDE.md.
